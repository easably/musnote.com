# Один API для сайта и приложения

Запрос пользователя 2026-11-21. Один API с одним движком. Сайт умеет то же, что приложение, приложение — то же, что сайт.

## Как сейчас (по коду)

| | Сайт | Приложение |
|---|---|---|
| Адрес | `https://api.musnote.com` | `https://api.musnote.com` |
| Вызов | `POST /v1/piano-notes` (`web/assets/js/page-audio-to-piano-notes.js:418`) | `POST /v1/separated-notes` (`lib/services/separated_notes_api.dart`) |
| Что получает | один общий список нот со всей записи | шесть дорожек, ноты по каждой |

На сервере это **два разных сервиса и две копии кода**:
- `api/` — `/v1/piano-notes`, Basic Pitch по всей записи. Выкладка — GitHub `Deploy notes API`, проверка — `scripts/integration-notes-api.sh`.
- `probe/server7/` — `/v1/separated-notes`, Demucs + Basic Pitch по дорожкам. Это «проба»: ставится руками, в workflow и проверках её нет.
- `notes.py` скопирован в обе папки, различаются только имена (`notes_from_recording` / `notes_from_audio`).

Сеть: Caddy на server1 → туннель на server8 → server7. Оба сервиса работают на server7, server8 только пересылает трафик.

Итого: домен один, а движков два. Сайт и приложение показывают разное: на сайте нет дорожек.

## Как должно быть

1. **Один сервис `api/`.** Код дорожек переезжает из `probe/server7/` в `api/` и становится основным. Один образ (GPU, Python 3.10: Demucs + Basic Pitch), один `notes.py`, одна выкладка через GitHub workflow, одна проверка в CI. Папка `probe/server7/` уходит.
2. **Один вызов для обоих клиентов — `/v1/separated-notes`. `/v1/piano-notes` убираем**, когда сайт перейдёт на дорожки (решение пользователя 2026-11-21).
   - **Сервер один, путь один, а движков снятия нот внутри может быть несколько** — для опытов: какой быстрее, какой точнее.
   - Параметр `engine` в запросе, необязательный: `POST /v1/separated-notes?engine=basic-pitch`. Без параметра — движок по умолчанию.
   - В ответе поле `"engine"`: каким движком сняты ноты.
   - Клиенты (сайт и приложение) параметр не передают и получают движок по умолчанию.
   - Движки подключаются одним интерфейсом (`notes_from_audio(path) -> list[note]`) в `api/app/engines/`. Сейчас движок один — Basic Pitch. Новые добавляются отдельными задачами, без смены пути и формата ответа.
3. **Сайт = приложение по главному сценарию:**

   | Возможность | Сайт сейчас | Приложение | Сделать на сайте |
   |---|---|---|---|
   | Загрузка файла до 100 МБ | есть | есть | — |
   | Запись с микрофона | нет | есть | кнопка «Записать» в зоне загрузки (MediaRecorder) |
   | Дорожки: выбор, «тихо», «без нот» | нет | есть | список дорожек, как в приложении |
   | Итог «Найдено N нот · время · диапазон» | по всей записи | по дорожке | по выбранной дорожке |
   | Падающие ноты + клавиатура | есть | есть (весь экран) | по выбранной дорожке; кнопка «Во весь экран» |
   | MIDI | один трек | дорожка или все (один файл, трек на дорожку) | переключатель «дорожка / все» |
   | Лист с буквами (PDF) | печать | файл | по дорожке или все, разделы по дорожкам |
   | Текст, копировать | есть | есть | по дорожке или все |
   | «Нот не нашлось» | нет | есть | то же состояние |
   | Список сохранённых записей | нет (нет аккаунтов) | есть, на телефоне | **не делаем**: сайт без логина, хранить негде |

   Логику (имена файлов, MIDI format 1, фразы для PDF и текста) держать одинаковой: `web/assets/js/notes-export.js` ↔ `lib/services/notes_midi.dart`. Общие контрольные значения — в тестах на обеих сторонах, как у падающих нот.
4. **Сеть — убрать server8 из пути.** Пользователь назвал три варианта (2026-11-21). Исполнитель собирает факты, выбирает пользователь:
   - **(а) Проброс порта к server7.** До server7 снаружи уже доходит SSH через `185.152.136.209:1003` — это NAT роутера. Так же пробросить порт API (например `185.152.136.209:<порт>` → server7 `:8095`), а прокси на server1 будет ходить туда. Порт открыть **только для адреса server1** (фильтр на роутере или firewall server7): API без авторизации. Внимание: пользователь говорит, что на server1 nginx, а по прошлой проверке на 443 там Caddy (`caddy_proxy`) — уточнить, кто принимает `api.musnote.com`.
   - **(б) Перевезти server7 в локальную сеть server1** — делает пользователь, потом прокси ходит на LAN-адрес server7.
   - **(в) Запускать API на server1, если хватит видеопамяти.** Исполнитель меряет: пик VRAM на server7 при разборе Capaldi (`nvidia-smi --query-gpu=memory.used --format=csv -lms 500` во время запроса) и свободную VRAM, модель карты и драйвер на server1. Результат — таблицей в блоке.

   До выбора туннель через server8 работает как сейчас.

## Прогресс разбора (добавлено 22.11 по просьбе пользователя)

Сейчас `POST /v1/separated-notes` молчит до конца (до 180 с). Клиенты (сайт и приложение) хотят показывать правдивые фазы: очередь → разделение → поиск нот (дорожка k из n) → готово (N дорожек с нотами).

Варианты:
- **(1) Задания — рекомендую.**
  - `POST /v1/separated-notes/jobs` → `{id}`;
  - `GET /v1/jobs/{id}` → `{phase: queued|separating|transcribing|done|failed, stems_total, stems_done, position_in_queue, result?}`.
  - Плюсы: переживает сворачивание приложения и обрывы мобильной сети; не упирается в 180-секундные таймауты Caddy и туннеля; легко добавить очередь при нескольких клиентах.
  - Минусы: результат нужно хранить до забора (TTL 10 мин, затем удалить — текст политики «аудио удаляется сразу после ответа» поправить на «после выдачи результата, не позже 10 минут»).
- **(2) Поток в том же запросе** (NDJSON / SSE: строки-события, последняя — результат). Меньше кода, но в Caddy нужен `flush_interval -1`, и при обрыве связи результат пропадает.

Старый синхронный путь оставить, пока сайт и приложение не перейдут. Поле `engine` (выше) — и в заданиях.
